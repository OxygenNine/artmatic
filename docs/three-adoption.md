# three.js 接纳方案

一句话结论：**该接纳的是「Agent 自由写代码」这条创作通路，不是 three 的渲染器**。
两者相邻但不等价，混为一谈会把工程预算花错地方。

---

## 1. 先复核那四张对比图

四段「three.js 版」代码（工程里 3.7–5.7 KB）读下来是同一形态：

```js
const mat = new THREE.ShaderMaterial({ uniforms:{uT,uRes,uSeed}, vertexShader: V, fragmentShader: F });
const q = new THREE.Mesh(new THREE.PlaneGeometry(2, 2), mat);
// 顶点着色器：gl_Position = vec4(position.xy, 0.0, 1.0)
```

**它们全是全屏 quad + 手写 GLSL 光线步进**，没有场景图、没有深度、没有灯、没有任何
three 特性，除了「提供一个装 GLSL 的壳 + 传 uniform」。四段都是（含标着「测地线」的
黑洞）。另一路复核材料（池核 / 阈限空间那次会话）里同样是 14 处 `ShaderMaterial`、
0 处 `BoxGeometry`。

所以那 2–12 倍不是我抄你、你抄我的同一段着色器的比较，而是**两套不同作者写的两套
着色器**的比较。倍率的来源是「谁写得更省」，不是「谁的渲染器更快」。

### 实测（逐帧成本）

同一工程、同一条轨、同一分辨率、逐帧换 t，连渲 24 帧后一次回读求均值
（Win10 / Chrome / RTX 4070 / 预览 700×394，每组的非黑像素都复核过）：

| 场景 | three 片段 | 内置生成器 | 倍率 |
|---|---|---|---|
| 蒸汽波大陆 / 地平线 | 6.5 ms | 19.0 ms | 2.9× |
| 废墟管道 / 3D 隧道 | 3.5 ms | 43.8 ms | 12.5× |
| 门格海绵 | 1.7 ms | 9.7 ms | 5.6× |
| 黑洞 | 8.7 ms | 18.0 ms | 2.1× |

按像素线性外推（预览 960×540 ≈ 1.9×，导出 1920×1080 ≈ 7.5×）：three 版在预览
3–17 ms、导出 13–65 ms；SDF 版在预览 18–83 ms、导出 73–330 ms。

这和「three 顺、algo 卡」的手感是同一件事的两面：240 Hz 的预算是 4.16 ms/帧，
three 那 1.7–8.7 ms 落在「贴着预算到明显够用」的区间，SDF 的 9–44 ms 直接出界。

### 底栏那个 240 到底在数什么

它数的是 **rAF tick 次数**（`appState.countFrame`，每帧一次，上限 = 显示器刷新率），
不是「真的上屏了几帧」。这个区别在这种场景下会骗人，我实测到一个反例：

| 场景 | 底栏 fps | 非黑像素 | 强制逐帧渲一次 |
|---|---|---|---|
| `tunnel-3d`（首帧之后 2.5 s） | **240** | **0 %** | 627 ms |
| `horizon` | 65 | 100 % | 18.6 ms |

也就是：**画面全黑、着色器还在链接时，计数器照样读 240**。它只能说明「主线程没被
拖住」，不能说明「画面在动」。反过来说，你机器上 three 片段读 240 且画面流畅，是
真的 —— 主线程每帧只有 1–2 ms（下发 + 一次纹理上传），剩下的都在 GPU 管线里排着。

两件事因此成立，且互不否认：

1. three 不谎报：它的每帧成本确实低一个量级，240 的读数是主线程真的没被拖住。
2. 状态栏的读数有盲区：它分不清「渲得快」与「这一层根本没出图」，而后者正是
   「编译着色器几秒黑屏」时它在显示的东西。**这是要修的**（见 §4 阶段 3 末）。

### 编译：这才是用户能直接看见的那一刀

`tunnel-3d` 这种重着色器的链接是**秒级**的（`AGENTS.md` §1.3 记过 4.7 s 那一次）。
链接期间这一层缺席、画面全黑，而预览循环与计数器毫无察觉 —— 观感就是「点上去先黑
两秒」。three 那四段编译在 100 ms 量级（整个模块首次载入 + 内部着色器一次性），
所以「three 没有编译黑屏」不是错觉，是它的着色器单元小得多。

这一条对方案的影响比性能更大：**编译时间应该进生成器的成本模型**，而不只是帧时间。

### 顺带一个与本方案无关的坏消息

内置生成器本身超预算：**隧道 43.8 ms/帧 @700×394**，换成 960 宽就是 80 ms 量级；
再加上秒级的编译等待，它在时间轴上目前是「点了先黑两秒、之后 12 fps」。这不是 three
的问题，是「这台机器上那几个生成器不能用」。无论 three 怎么接纳，这件事都得单独处理
（见 §4 阶段 3）。

## 2. 诊断：赢在哪，没赢在哪

| | 结论 | 依据 |
|---|---|---|
| Agent 写自由 GLSL | **赢，而且是大头** | 四段代码 3.7–5.7 KB、一次成型、观感超过手写库；模型对「three + 裸 GLSL」的熟练度远高于对本项目 `defs/glsl` 协议（EFFECT_HEAD / 参数声明 / glob 配对 / uniform 命名）的熟练度 |
| three 的场景图（几何 / 深度 / 灯 / 材质） | **未验证** | 四段里一次都没用。这是能力赌注，不是已证实的性能收益 |
| three 的渲染器本身 | **与 SDF 不可比** | 两者都是逐像素着色。SDF 的代价在步数与着色，几何的代价在填充率与 draw call。哪种便宜取决于内容 |
| three 的编译 / 首帧 | **赢，且用户能直接看见** | 一个 program、内部着色器一次性，约 100 ms；SDF 生成器是秒级链接，期间画面全黑（实测 2.5 s 后仍 0 % 非黑像素） |
| three 的 EffectComposer / 后处理 | **不该用** | 本项目的 90 个特效 + 120 余条转场全是全屏 pass，已经是最便宜的形态；搬进 three 只会更慢，还会把确定性拆掉 |

真正的信号只有一个，但它足够值钱：**Agent 会绕过我们的着色器协议，把 GLSL 塞进
一个 three 片段里跑**。这不是它在偷懒，是我们在给它的接口太贵。所以要接纳的是
「自由代码片段」这一层，three 只是这一层的宿主。

---

## 3. 目标形态：三层，一个运行时

```
① sketch clip   代码即内容，无参数，只给 Agent                ← 已经有了（实验分支）
② program       代码 + 声明的参数表，用户可拖滑块                ← 已落地（阶段 1）
③ generator     库内置的 three 生成器（几何场景），进选择器      ← 能力赌注，先做两个
```

三层共用同一份 `src/three/runtime.ts`（独立上下文、每消费方一张纹理、懒载），差别只在
「参数从哪来」与「谁能改」。**不要为 ②③ 各写一套渲染路径** —— 那正是本项目反复记录的
那类 bug（「试炼场里好好的、主应用里某类源不工作」）。

## 4. 分阶段

### 阶段 0：把实验品坐实（已基本完成）

- ✅ 试跑回执从「没抛异常」升级为 `{ drawCalls, filled }`：`drawCalls>0 && filled=0`
  就是「画了但一片空白」，这个形态（相机在近平面里、顶点着色器写错、alpha=0）
  **不会抛任何异常**，只看异常时与「场景本来就是空的」完全一样。
- ✅ 写代码 → 编译 → 真尺寸试跑 → 回执；`three_status` 可按需重跑。
- ⬜ 时间轴缩略图（现在是一块空白块）。复用 `render/algo-thumb-renderer.ts` 那条路。
- ⬜ 契约里补两段：怎么判断「没画出来」；场景图与全屏着色器各给一个最小例子
  （现在只给了场景图那条，模型于是默认走它；反过来也一样容易偏）。

判据：四段复核工程能直接在 app 里播放；故意写坏的三种（语法错 / 运行期抛 / 画了全空）
各自给出不同的回执。

### 阶段 1：program（带参数，用户可编辑）—— 已落地

这是补上 §1.9 那个洞的地方。现状：`params()` 声明 → 检查器画控件 → 值落在
`source.params`；Agent 用 `set_three_params` 改值（未知键拒掉并回 `validIds`）。
素材同时接上：`ctx.texture(assetId)` 只给**图片**（视频留到需要时再说）。

**插件代码池（阶段 1.5，已落地）**：插件清单多了 `three: [{ name, label, code }]`
（API v4），片段用 `ref` 引用。它解决的是「同一套代码喂十条片段，改一处全都变」——
把这份重复留给用户去复制粘贴，等于让工程在第三次改稿时散架。三条实现约束写在
`src/plugins/AGENTS.md`：装载即编译、停用的插件不提供代码、引用型片段不接受
`set_three_code`。

**关键帧还没做**，而且优先级不高：时间驱动的量本来就该写在 `update(t)` 里，那是
代码的强项；关键帧真正的用处是「用户想按时间轴改光强」，那要等有人真这么用再说。

- 代码里声明参数（形式待定，见 §6）：
  ```js
  function params() { return [ { key:'hue', type:'range', min:0, max:1, default:0.5 } ]; }
  function create(THREE, ctx) { /* ctx.params.hue 每帧给当前值（含关键帧 / 调制） */ }
  ```
- 参数**不重建场景**：值以 `ctx.params` 的形式每帧传进去（与 `realtime` 生成器同一条
  约定）。声明 `rebuild:true` 的键才重建 —— 那是少数（几何尺寸、分段数）。
- UI 复用 Inspector 现有的 `ParamDef` 渲染与 `KeyableField`；agent 侧复用 `set_curve`
  的键空间。
- 判据：给四段复核代码各加 2–3 个参数后，用户能不碰代码改配色 / 速度 / 密度，且
  改参数不触发重建（帧时间不出现尖峰）。

### 阶段 2：three 生成器（能力赌注，先做两个）

- `algos` 新增 `kind:'three'`：def 提供 `build(params) → { scene, camera, update, resize }`。
  参数、关键帧、缩略图、导出、Agent 工具全部继承现有的，不需要新接口。
- 先做两个能证伪的样本：
  1. **几何场景**：镜面地砖 + 体积灯（「池核 / 阈限空间」那类）—— 测「场景图是否比
     手写 SDF 更好写、够不够快」。
  2. **instanced 大量重复体**：栅格 / 管道 / 方块阵列 —— 测「几何实例化 vs SDF 域重复」
     的真实代价，这是几何唯一有结构性优势的形态。
- 判据：两个都在 960×540 预览下 ≤ 8 ms；且**这两个如果模型还是写成全屏着色器**，
  就把 §2 那行「未验证」改成「不成立」，停止阶段 2，把预算挪回阶段 1。

### 阶段 3：SDF 库的成本体检（与 three 无关，随时可做）

- 43.8 ms 的隧道等于在时间轴上不可用。两条路选一条：加 quality 参数（步数 /
  内部分辨率 / 噪声层数），或按 §2 的结论把「必须有几何」的那几个改写。
- **把编译时间算进成本模型**：`tunnel-3d` 的链接是秒级的，而它和帧时间一样花用户的
  时间。要么拆 program / 缩着色器，要么在预览里把它变成可见的「编译中（预计 4 s）」
  而不是一块黑。
- **底栏读数补一个信号**：`pendingCompiles > 0` 时不该读 240。要么显示「编译中」，
  要么把「这一帧真的出了图」算进统计（`readPixels` 太贵，退一步：着色器就绪 +
  draw call > 0 也算便宜的近似）。
- 判据：四个重场景在 960×540 下 ≤ 16 ms；首帧到出图的等待 ≤ 500 ms；编译期间
  界面有明确提示、且读数不撒谎。

## 5. 不做什么

- **不把合成器 / 特效 / 转场迁到 three**。它们是全屏 pass，已经是最省；three 的
  EffectComposer 更慢，而且会把「预览与导出同一条求值路径」这条硬约束拆掉。
- **不做双渲染栈**（一边 WebGL2 自研、一边 three 各管一半画面）。一个 `kit.gl`，一份
  合成链；three 只负责产出「一张源纹理」。
- **不开放 `three/addons/*` 全量**。`GLTFLoader` / `Reflector` / `EffectComposer` 这些
  一旦进契约就是长期兼容负担；先做白名单，一次加一个。
- **不给用户代码编辑器**。program 给的是参数面板，不是 JS 框。

## 6. 已定与待定

已定：

1. **参数声明 = `params()`**（函数）。执行它是纯 JS、不需要 THREE，检查器与写入端
   读同一份；静态数组的好处只是「不必执行代码」，在这里不成立。
2. **素材走 `ctx.texture(assetId)`，先只给图片**。它拿的是**已解码的源**、由 three
   在自己的上下文里上传一份 —— 所以「异步解码 vs 同步 resolve」这条缝没有被打破，
   没解码好就是 `null`，下一帧补上。

待定：

3. **视频帧**要不要给。给了就得在 `resolve` 里塞一个「这一帧解好了没有」的同步查询，
   以及「换素材 / 跳帧」时的失效逻辑；那是视频取帧那套（`engine/video-source.ts`）
   的一半工作量。
4. **SDF 生成器的处置**：加 quality 参数（便宜、画面要接受降级）还是分批改写
   （贵、一次到位）。

## 7. 会咬人的地方

- **显存**：每片段 × 每消费方一张纹理。导出分辨率下 1920×1080×4 ≈ 8.3 MB，
  三个消费方 = 25 MB/片段；10 个 three 片段就是 250 MB。要么设上限，要么让
  `recall` / `bake` 复用主链那张（那会把「闪回里混进播放头那一层」放回来，见
  `src/three/AGENTS.md` 第 2 条）。
- **导出时间**：黑洞那段 1080p 约 65 ms/帧，30 秒 @30fps = 58 秒。要有进度与预估，
  不能像现在这样只给一个百分比。
- **首帧**：three 上下文 + 内部着色器编译约 100 ms，一次性但会卡在第一帧。导出前要
  预热（`Renderer.setPrewarm`），否则第一个导出帧就吃这个尖峰。
- **确定性**：three 渲染器本身确定；不确定的是「代码里攒状态 / `Math.random()`」。
  sketch clip 明确不承诺；program 要在契约里写死「从 t 求值」，并提供注入的
  `ctx.rand`（按 `seed + clipId + 帧号` 派生），否则预览缓存与导出会各给一版画面。
- **模型失败模式**：相机贴在近平面上、顶点着色器写 `w=0`、材质 alpha=0 —— 都已用
  `drawCalls/filled` 兜住；但**这两项只在试跑那一帧成立**，时间轴上后面某一帧才空
  的情况仍需 `render_frame` 复核。
