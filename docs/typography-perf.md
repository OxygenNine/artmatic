# 排版性能画像与优化候选

> 调研（2026-11-05）。**没有改任何生产行为**：下面所有数字来自临时埋点 + 现成
> `__artmatic.typoRasterize`（与预览同一条 `rasterize` 路径），埋点已移除。
> 复测方法见 §2，改动前先重测一遍（机器不同，绝对值会变，形状不会）。

## 1. 结论

排版吃性能的地方**只有一处**：`TypographyRuntime` 为了得到一帧画面，必须让
snapDOM 把整份文档**重新捕获成一张位图**。

- 单次捕获 **13–30 ms**，其中 **12–14 ms 是空文档也要付的固定开销**；
  内容只加 3–10 ms。分辨率与超采样密度几乎不影响（**不是像素受限**）。
- 动态文档（元素动画 / 镜头关键帧 / 脚本）**每帧一次捕获** ⇒ 33 ms 的预算是
  不够的，天花板就在 30 fps 上下；元素一多、镜头一缩放到 2× 就是 20 fps。
- 静态文档零成本（键里帧号是 `null`，整个片段只烘一次）。**「会动的排版」与
  「不会动的排版」是两个数量级**，讨论性能时必须先分开。
- GPU、上传、JS 建模、字体子集化都不是瓶颈（见 §3 的分项）。

因此优化只能在**捕获链的外面**做：**少捕获**（帧率量化 / 把镜头与元素动画
下放到合成器 / 文件级预览代理）、**少排队**（在飞去重）、**让捕获本身便宜一点**
（snapDOM 缓存）。降分辨率、换捕获库、多线程都不解决；**换掉 DOM 捕获路线
（自研渲染器）已明确否决**（见 §4 末尾）。

## 2. 测量方法

- 页面里用 `__artmatic.typoRasterize(doc, w, h, 0)` 串行跑 3 次取中位数；
  它内部就是 `TypographyRuntime.rasterizeOnce → backend.rasterize`，与预览
  `resolve` 走同一个后端、同一份 `buildDocDom`。
- 分段耗时用临时埋点（`fonts.ensure` / `ensureDocImagesFx` / `buildDocDom` /
  `bakeAnimations + runScripts` / `snapdom()` / `toCanvas()` / `shrinkCanvas`）。
- 播放：`appState.play()` 后 2 s 窗口，统计 rAF 次数、`[perf-dom]` 次数
  （= 真正完成的捕获数）与 `playT` 推进量。
- 环境：开发机（4070 Laptop / 8 GB 显存），Chrome headless（rAF 不限帧，
  绝对值偏高；每次捕获的耗时与真实 60 Hz 环境同一量级）。

## 3. 数据

### 3.1 单次捕获的分段耗时（density 1，单位 ms，中位）

| 文档 | 目标尺寸 | fonts | build | snap | toCanvas | 合计 |
|---|---|---|---|---|---|---|
| **空文档** | 1280×720 | 0.2 | 0.1 | **13.2** | 0.3 | **13.8** |
| 空文档 | 1920×1080 | 0.4 | 0.0 | 12.0 | 0.3 | 12.7 |
| 1 文本 | 1280×720 | 0.2 | 0.2 | 18.7 | 1.5 | 20.8 |
| 1 文本 | 1920×1080 | 0.4 | 0.2 | 18.2 | 1.8 | 20.7 |
| 3 图形（渐变/描边/阴影） | 1280×720 | 0.2 | 0.9 | 21.2 | 0.3 | 22.6 |
| 3 图形 | 1920×1080 | 0.4 | 0.2 | 15.7 | 0.3 | 16.6 |
| 3 文本 + 3 图形 | 1280×720 | 0.3 | 0.4 | 22.1 | 2.0 | 24.8 |
| 3 文本 + 3 图形 | 1920×1080 | 0.3 | 0.7 | 29.4 | 1.7 | 32.4 |
| 1 文本（系统字体 Arial） | 1920×1080 | 0.6 | 0.1 | 15.0 | 0.3 | 16.0 |
| 1 文本 + 镜头 2×（density 2） | 2560×1440 | 0.3 | 0.2 | 19.6 | 1.5 | 21.7 |

三个直接读出来的事实：

1. **空文档 13 ms** —— 固定成本 = 「克隆 DOM → 内联样式 → 序列化成
   SVG(foreignObject) → 当图片解码 → drawImage」这一整趟，与内容无关。
2. **1280 与 1920 差 ≈1 ms**，2560×1440 的 density 2 也只贵 1–2 ms ⇒
   **不是像素/带宽受限**，是「每次都新建一个图片文档并重排一次」的固定成本。
3. 内容线性但斜率小：3 文本 + 3 图形比 1 文本多约 6–10 ms。

其余分项都很小：`buildDocDom` 0.2–0.9 ms、`fonts.ensure` ≈0.3 ms、
`ensureDocImagesFx` ≈0、`shrinkCanvas` ≈0.1 ms；`texImage2D` 上传
（1056×594）**0–1.2 ms**，而且是异步的。

### 3.2 snapDOM 自己的持久缓存（`cache` 选项）

`cache: 'disabled'`（我们现在的设置）每次捕获前清空 snapDOM 的
持久 style/resource 缓存；`'soft'` 复用。只改这一个词，`snap` 段：

| 文档（1920×1080） | disabled | soft |
|---|---|---|
| 空文档 | 12.0 | 7.8 |
| 1 文本 | 18.2 | 7.3 |
| 3 图形 | 15.7 | 9.0 |
| 3 文本 + 3 图形 | 29.4 | 17.0 |
| 1 文本 + 镜头 2×（2560×1440） | 19.6 | 8.5 |

≈**2×**。把 26 条排版 E2E（含「同参数同结果」「两次导出同一帧字节一致」
「动画真的被 seek 到 t 上」）全部跑在 `'soft'` 下也全绿 —— 但见 §4 A0 的风险。

### 3.3 真实播放

2 s 窗口、时间轴上一个带镜头关键帧的排版片段在播放头下：

| | rAF | 完成的捕获 | playT 推进 |
|---|---|---|---|
| `cache: 'disabled'` | 142/s | 25 次（12.5/s） | 1.70 s / 2.00 s（85%） |
| `cache: 'soft'` | 213/s | 18.5 次（p50 15.5 ms） | 1.71 s / 2.00 s（85%） |

两点：**播放头只有 85% 实时**（重排版把主线程拖慢，`playT` 是 rAF + dt 推的），
以及捕获链在预览尺寸下大约每秒 25–65 次（取决于缓存开关与争用）——
这就是「30 fps 顶天、视差 20 fps」的来源。

## 4. 候选方案

按「收益 / 成本」排序。编号供讨论用，不代表实施顺序。

### A. 小改动（当天可做）

- **A0｜`cache: 'soft'`**：单次捕获 ≈2×（§3.2）。一行改动。
  **风险**：缓存对我们是黑盒。最可疑的是**图片素材**——同一个 `resolveImage`
  URL 若在磁盘上换了字节（linked 素材原地修改），可能拿到旧图。
  建议先补一条「换图后必须重烘」的 E2E 再开，并记住 `'soft'` 是 v3 的默认值、
  我们当初选 `'disabled'` 是为了躲「上一帧的样式」。
- **A1｜别排无效捕获**：`inflight` 现在按**精确键**去重，播放时 30 fps 会给
  30 个不同的键各排一次捕获。改成「同一 `(doc, size, 模式)` 已有在飞就跳过」，
  主线程只按**能完成的速率**烘，其余帧继续用 `latest` 顶上。
  收益：帧率不变，但**交互不再被排满**（现在一半的 rAF 时间花在白排的捕获上）。
- **A2｜播放时跳过超采样**：`density` 只在「暂停/静止」时用 2×，播放中恒为 1。
  省 1–2 ms + 一次 4× 面积的 canvas（内存/上传），画面只会略软。

### B. 少捕获（中等改动，收益 2–10×）

- **B1｜帧率量化**：动画文档按 `floor(frame / 2)` 烘焙（15 fps 的排版层），
  **键与 `localSec` 都用同一个量化后的 t**（保证确定性、不出现「图像相位与
  播放头不同步」）。捕获次数直接减半。可做成偏好（30 / 15 / 10）。
  **代价**：脚本拿到的 `ctx.t` 也是量化值，必须在能力清单里说清。
- **B2｜把镜头下放到合成器**（专治视差）：同一 `depth` 的层，镜头是一个
  **相似变换**（平移 + 旋转 + 缩放）。把它从「烘进位图」挪到「合成器的四边形
  矩阵」，镜头动画时**一次捕获都不用**，还能顺带解决导出时的逐帧烘焙。
  前提条件（按工作量）：① compositor 的 `placeLayer` 支持四边形旋转（现在
  只有平移/缩放）；② 按「片段内最大 zoom」烘一次（内存换时间，注意
  `capacity.ts` 的位图上限）；③ 画布外留边（overscan），否则摇镜头会露边。
  **限制**：元素 `depth` 不同时要拆成 N 层（每个 depth 一个四边形）。
- **B3｜把元素动画下放到合成器**：元素动画（transform / opacity 类）现在也是
  烘进位图。理论上每个元素一个四边形就能交给 GPU —— 这就是「排版图层化」，
  是 B2 的一般化版本。工作量大于 B2（要拆层、要处理混合模式与层叠顺序、
  阴影/滤镜仍得烘焙）。

> **「换掉 DOM 捕获路线」（自研 GL/排版渲染器）已明确否决**（2026-11-06）。
> 排版复用 HTML + CSS Animation + snapDOM 的全部价值就是**不维护一个 HTML
> 渲染引擎**：真要自己画文字与图形，等于手搓连字/行盒/混合/滤镜/富文本，
> 或者让 Artmatic 同时维护两套排版子系统。所以优化只能在这个捕获链的**外面**
> 做（少捕获、少排队、缓存），不许换成「另一条渲染路径」。

### D. 文件级预览代理（讨论中，2026-11-06）

思路（用户提的「邪恶方案」）：排版一段时间没改动，就把**排版片段覆盖的时间段**
烘成一段低码率 MP4 落在工程目录里；播放时直接解码这段视频，不再逐帧捕获。

**数字（本机实测外推）**

- 收益：捕获 13–30 ms/帧 → 解码一帧 H.264 约 0.5–2 ms（`video-source.ts`
  已有「按 t 取帧 + 有界纹理缓存」）。拖动播放头同样受益（20 ms → 2 ms/帧）。
- 体积：按**当前预览渲染尺寸**（1056×594）而非它的 50% —— 文字是内容的全部，
  砍分辨率就是砍唯一的清晰度来源。30 fps、1.5–3 Mbps：
  每 8 s ≈ 1.5–3 MB，60 s ≈ 11–22 MB，3 min ≈ 34–67 MB。「十几到几十 MB」成立。
- **预渲染时间 ≈ 1:1 实时**（240 帧 × 13–30 ms ≈ 3.5–7.5 s / 8 s 内容，A0 之后
  约 2:1）。也就是**第一次播放是亏的**，第二遍起才赚 —— 这与「改完反复审阅」
  的实际用法对得上，但必须接受「空闲时占用 CPU 与片段等长」。

**三个硬约束（都不是调参能绕开的）**

1. **alpha**：H.264 没有 alpha，而排版层要叠在别的片段之上。两条路：
   - VP9-alpha（WebM）：浏览器能放，但 **WebCodecs 解码是否保留 alpha 需要先做
     spike 验证**（`mediabunny` 能否写也是问题）；
   - **颜色 + 辅助 alpha 视频**（把 alpha 存进第二路的亮度），着色器里相乘。
     确定可实现、码率 ×2；透明处的 rgb 本来就是 0，边缘不会出现黑边。
   若不接受，就只能烘**整帧**（= 范围内所有轨道合在一起，DaVinci 的 render in
   place），下层任何改动都失效。
2. **失效**：编辑即失效。它只对「改完 → 反复审阅」有效，对正在调参的人是纯负担。
   需要：空闲 1–2 s 才启动、可取消、任何编辑立刻丢弃、绝不阻塞预览。
3. **有损**：文字是编码器最不擅长的内容，1–2 Mbps 的标题卡会有蚊噪/振铃。
   宁可码率放到 3–5 Mbps（体积翻倍），也别让用户觉得「预览变糊了」。

**架构落点比想象中顺**（这也是它值得考虑的原因）

- 编码：复用 `runExport` 的逐帧驱动 + `frame-sink`（WebCodecs），只是 source 换成
  「只糊这一层」、sink 换成写缓存文件；
- 解码：复用 `engine/video-source.ts`；
- 命中：`TypographyRuntime.resolve` 加一条「代理命中」分支，返回同一个
  `SourceTexture`；
- 键几乎现成：`docHash | 尺寸 | 模式盐`（上一轮为缺帧回退拆出来的桶键）**但要补
  `doc.camera` 与 seed / fps** —— `docHash` 刻意不含相机（逐帧视差由第 5 段表达），
  而段缓存需要「基准相机」也进键。
- 工程目录多一个 `cache/preview/`：`analysis/`（音频分析 + 缩略图）已有「派生物
  放工程目录」的先例；要进 `PROJECT_DIRS`、写进 `src/project/AGENTS.md` 的
  「可丢弃」清单，默认关闭 + 体积上限 + 一键清除，打开/保存绝不碰它。

**判断**：可行，但**顺序上排在 A0 / A1 / B1 之后**。这三条把 20 ms 压到约
5 ms/帧均摊，30 fps 大概率够用；如果压完仍不够（重排版、慢机器、长片段），
再用文件代理 —— 它的前置成本（alpha 方案 + 缓存治理）和收益面（只对重复审阅
有效）都不如前三条。

一个更小也更准的变体：**代理只用于播放与拖动，暂停永远走精确位图**（现在暂停
本来就命中缓存）。这避免了「拿压缩图判断排版」的最坏情况，成本不变。

### D2. 已确认无效 / 不要做

- **降分辨率 / 降预览画质**：1280 与 1920 只差 1 ms。`previewScale` 只省显存与
  上传，不救帧率 —— 别把它当性能开关宣传。
- **只截可见区**：版式本来就只在画布内，收益≈0。
- **Worker / OffscreenCanvas**：snapDOM 需要真实 DOM，`foreignObject` 排版
  在 worker 里跑不起来。
- **并发多张**：后端是串行链（`host` 共享，见 `backends/dom-snap.ts` 的注释），
  且每张都有 13 ms 固定成本，拆开只会更慢。
- **换捕获库**（html2canvas 等）：固定成本来自「SVG + 图片解码」这条路线本身，
  换库改变不了形状。

## 5. 建议

1. **A0 + A1** 先落地：一个词 + 十几行，捕获量减半、交互不再被排满；
   A0 需要补一条「换图后重烘」的守卫。（2026-11-06 已落地，见 §6）
2. **B1** 作为用户可见的偏好（「排版预览帧率」），对 20 fps 的视差最直接，
   且实现只需一个量化函数 + 键里换值。
3. **B2** 取决于产品判断：视差如果是重点功能，它是唯一能让镜头动画「几乎
   免费」的方案；否则不值得为它改 compositor。
**不做的事**：换掉 DOM 捕获路线（自研 GL 渲染器 / 第二套排版子系统）——见 §4 末尾。

## 6. 落地与复测（2026-11-06，A0 / A1 / A2，未做 B）

三处改动，都在捕获链的外面，**没有动渲染路径**。

> A1 的实现比本节原来的描述更保守：去重槽位是 `片段 id|位图尺寸`，不是
> 「(doc, 尺寸, 模式)」桶。原因是**同一份文档可以被两条片段各用一次**（复制出来
> 的标题卡，起点不同、时间上重叠），它们同桶却是两个不同的 `localSec` ——
> 按桶去重会让其中一层显示另一层的那一帧。桶里「同一条片段的别的帧」才是
> 该跳过的过期候选。

| 编号 | 落点 | 内容 |
|---|---|---|
| A0 | `backends/dom-snap.ts` | `cache: 'disabled'` → `'soft'`（复用 snapDOM 的持久 style / resource 缓存） |
| A1 | `runtime.ts::schedule` | 预览的异步烘焙**同一层只留一单**：去重槽位 `片段 id\|位图尺寸`，已有在飞就跳过 |
| A2 | `camera.ts::rasterDensity` + `runtime.ts::densityFor` | 超采样密度策略：播放中恒 1，导出 / 一次性烘焙永不降 |

### 6.1 复测方法

`.codebuddy/tmp/2026-11-06/perf.mjs`（同脚本跑改前 / 改后，各自 `vite build` +
`vite preview` + 无头 Chrome，视口 1600×900 ⇒ 预览渲染尺寸 878×494）：

- 单次捕获：`typoRasterize(doc, 1280, 720, t)` 串行 6 次取中位数（前两遍预热丢弃）。
  ⚠️ 这个接口自带 `getImageData` + 全像素循环，实测 **≈3ms** 固定开销也在计时里，
  所以绝对值比 §3.1 高约 3ms，**只用于前后对比**。
- 播放：`appState.play()` 后 2.2s 窗口，读 rAF 次数、`typoStats().rasters` 增量、
  `typoStats().pending`（新增读数：在飞单数）。
- 文档：一个带镜头 zoom 关键帧（1→2×）+ 三份文本（`depth = 1`）的排版片段，
  叠在 demo 的其余轨之上 —— 就是 §3.3 那条「视差最费」的场景。

### 6.2 单次捕获（ms，中位，含 ≈3ms 回读）

| 场景 | 改前 | 改后 | |
|---|---|---|---|
| 空文档 1280×720 | 16.4 | **11.5** | −30% |
| 3 文本（静态） | 34.2 | **22.8** | −33% |
| 3 文本 + 镜头 2×（density 2） | 37.6 | **28.8** | −23% |
| 同上，density 1（A2 的对照） | 31.5 | **23.0** | −27% |

A0 的收益与 §3.2 的预测（≈2×）方向一致、幅度小一些：本表是**整条 `rasterize`**
（含 `buildDocDom` / 字体 / canvas 回读），不是 snap 段。

密度本身的代价也读得出来：`density 2` 比 `density 1` 贵 **≈6ms**（改前 6.1、
改后 5.8）—— 这就是 A2 在播放中每帧省下的量。

### 6.3 播放（2.2s 窗口，两次独立测量）

| | 改前 | 改后 |
|---|---|---|
| rAF / s | 88 / 88 | **149 / 145** |
| 完成的捕获数 | 70 / 86 | 82 / 116 |
| 在飞队列 max（`pending`） | 8 / 19 | **2 / 2** |
| `playT` 推进 | 1.94 / 2.17 s | 1.92 / 2.18 s |

（改后这一列另一次独立测量是 142 / 161 rAF/s、91 / 98 次捕获、`pending` 2 / 2 ——
形态一致，绝对值随机器负载浮动。）

三件事：

1. **主线程的自由帧多了 60–80%**（88 → 142/161 rAF/s）。这是「交互不再被排满」
   的直接读数 —— A1 之前队列一路涨（结束时有 19 单还排着，约等于 0.7s 的
   主线程尾巴），之后恒等于在屏的排版层数。
2. **完成的捕获数反而变多**（70 → 91）：A1 之后每一单都是「此刻真的要的」，
   不再有排队等着被丢弃的活；单子变便宜（A0/A2）之后吞吐自然更高。
3. **`playT` 推进没变**，因为它由音频时钟推进、**丢帧不会让它变慢**。
   所以「播放更实时」不是这三条的收益 —— 收益是「同样的画面，主线程空出来了」，
   以及拖动播放头 / 调参数不再和烘焙抢主线程。

### 6.4 守卫
