# 预览渲染缓存（D 的取代方案：整帧，不是逐层代理）

> 设计（2026-11-18）。**已落地并接线**（状态见 §11）。取代
> `docs/typography-perf.md` §D 的「把排版层烘成带 alpha 的 MP4」——那一条要解决的
> 是一层很贵，代价却是 alpha 编解码 + 逐层失效，而且只对排版有效。

## 1. 结论

把 **`[t0, t1)` 整段时间轴的全部轨道**按预览尺寸渲成一段 MP4，播放时直接解码这段
视频，不再走 `buildStack` + 合成。任何让帧变慢的东西（排版捕获、SDF 场景、粒子、
长特效链、蒙版递归）都被同一条路径覆盖。

它还顺手消掉了原方案的两个最贵的东西：

- **没有 alpha 问题**。整帧就是屏幕上的最终画面，预览底色是 `#000`（`Preview.svelte`
  的 `.preview`），按不透明编码与现在的显示逐像素同值。VP9-alpha 的 spike、
  颜色 + 辅助 alpha 的双路、帧内 alpha 分支全部不需要。
- **不需要新的失效模型**。键是整份工程，任何一个字节变了就整段失效 —— 与
  「缓存是派生物」这条定位一致，不需要推导「哪些层的改动不影响哪些层」。

## 2. 数字

捕获 13–30 ms/帧 → 解码 0.5–2 ms/帧（`engine/video-source.ts` 已有按 t 取帧 +
有界纹理缓存）。拖动播放头同样受益：20 ms → 2 ms/帧。

| | 值 |
|---|---|
| 分辨率 | 当前预览渲染尺寸（1600×900 视口 ⇒ 878×494） |
| 帧率 | 工程 fps |
| 码率 | 2–4 Mbps（文字多的画面往上取；宁可大一点也不让预览掉清晰度） |
| 体积 | 每 10 s ≈ 2.5–5 MB；60 s 工程 ≈ 15–30 MB |
| 生成速度 | ≤ 24 帧/s（**按墙钟限速**，见 §4 的「节奏」），**首轮是亏的** |
| 生成时主线程 | 一帧 ≈2–4 ms（渲 FBO 0.2 + 回读 1.5 + 构帧 0.4）；占空比 ≈1/4 |

## 3. 键与失效：**每段各自的签名**

```
sig(from, to) = fnv1a(stableStringify({
  ver, from, to, WxH, assetsRev,          // 全局的、真的影响像素的
  seed, fps, resolution, beatGrid, theme, customThemes,
  tracks: [{ kind, enabled, clips: 落在 [from/fps-3s, to/fps+3s) 的片段（原样） }]
}))
```

**一条缓存的生死只看它自己那一段**（`core/preview-cache.ts::rangeSignature`）。

- 在 50 s 处改一个片段，0–20 s 那一段**一个像素都没变 ⇒ 签名不变 ⇒ 照旧命中**。
  这是这份设计里最要紧的一条：文件名叫 `<sig>-<from>.mp4`，内容签名进名字，
  不同段落之间没有任何共享状态。
- 进签名的：全局影响像素的那些（`seed` / `fps` / `resolution` / `beatGrid` /
  排版默认主题 / 自定义方案 / `assetsRev`）、**每条轨道的 `kind` 与 `enabled`**
  （`affectDepth` 数的是「下方最近的 N 条启用视觉轨」，空轨也占位）、以及每条轨道上
  落在窗口内的片段（整段对象进哈希，含曲线 / 特效链 / 绑定 / 转场引用）。
- 窗口两侧各留 **3 s**：转场窗口会伸到剪辑点前后，片段也可能刚好从边界外一点开始。
  多算只会「多作废一次」，少算会**放出旧画面**。
- **不进**签名的：`name` / `sections` / `beatMarks` / `issues` / 选中 / 播放头 / 视图
  —— 它们不决定任何像素。`WxH` 是**取偶后**的尺寸（`core/dims.ts`），所以宽度抖动
  1 像素不会让整段作废。
- 命中判据（`usableEntry`）= 签名 + fps + 尺寸 + 帧区间全对；`validEntryAt` 在播放时
  顺手把**内容已经过期**的条目删掉（GC 只按几何回收，算不了内容）。

代价要说清：一段**内部**的任何改动仍然会作废整段（段是按镜头切的，20 s 上限）。
它不是「边调边看」的加速器，是「调完反复审阅」的加速器。

## 4. 生成

- **触发**：播放头静止、且距最后一次编辑 ≥ 1.5 s。播放中绝不生成（会和预览抢
  主线程，而那正是要避免的事）。**播放结束也会重新排一次**（`noteIdle`）——
  否则被播放打断的那一段永远不会续上，表现是「有时候流畅、有时候不流畅」。
- **范围**：按镜头切段（相邻 ≤0.5 s 合并，单段 ≤20 s），**从播放头所在段开始环形
  轮转**。一次只烘一段，下一段由下一次空闲（编辑 / 播完）接着做。
- **离屏**：帧渲进 `render/bake-surface.ts` 的 FBO 再回读 —— 可见画布一个像素都
  不动，所以预览**不冻**、也不改渲染尺寸（早期版本走 `runExport`，代价是烘 4 秒
  预览冻 4 秒）。
- **节奏**：由 `ui/preview-cache.ts::pump` 在**每个 rAF 的末尾**推进至多一帧，
  间隔 = `max(1000/24, 实测单帧成本 × 3)`。按帧而不是按 `setTimeout(14)`：
  240 Hz 屏上每帧预算只有 4.16 ms，每个 vsync 都烘一帧必然掉合成器的帧，
  而 JS 侧的 rAF 间隔看起来毫无异常（这就是「显示 240 fps 却体感很卡」）。
- **取消**：任何 store 变更、播放开始、切工程、关闭工程立刻取消并删掉半成品。
  取消粒度是**一帧**（下一步就不再推进）。
- **上限**：默认 1 GB，按 `capacity.ts` 派生的 `previewCacheMB` 兜底；
  超出按「最久没用」淘汰到 80%。

## 5. 播放

**那一段有缓存，就只用缓存。** 三种情况分得很清：

| 情况 | 画面从哪来 |
|---|---|
| 播放中，当前帧有有效缓存 | 解码队列里最接近的那一帧（不晚于本帧，容差 1.5 帧） |
| 播放中，队列一时没货 | **重复上一帧**并继续追，**绝不回精确合成** |
| 播放中，当前帧没有任何缓存覆盖 | 精确合成（这一段本来就没烘过） |
| 拖动播放头（暂停 + 250 ms 内） | **缓存**（随机访问解码，糊一帧无所谓） |
| 停手 / 暂停稳定之后 | 精确合成（锐利的定格） |

为什么「没货也不回精确合成」：精确合成一旦让帧率掉到 10 fps，播放头（音频钟）
反而跑得更快，队列就更追不上 —— 那是**正反馈**，不是抖动。缓存是「播放」的路径，
精确合成是「停下来看」的路径。

必须绕开缓存的路径（它们要的是"此刻精确"）：`onlyTrackId` 单轨观察、两帧并排、
编辑器截图、E2E 的 `__artmatic.renderFrame`、导出的 `prewarmFrame`。它们都不经过
播放循环，所以缓存挂在**播放循环**这一层就天然绕开了。

### 5.1 五件决定「缓存到底有没有用」的事（2026-11-18 加固）

第一版实测**命中率只有 79%**、而且每次命中还要付 11 ms 解码 —— 缓存开了几乎
等于没开。三处都改掉之后实测 89/90 帧命中、命中那帧的总开销 0.7 ms：

1. **解码走顺序迭代器**（`VideoSampleSink.samples()`）而不是 `getSample(t)`。
   后者是随机访问，每帧都要按关键帧重新定位（p50 **11 ms**、p90 27 ms、峰值
   250 ms），比它想省掉的合成还贵。播放是单调前进的，前进一帧只该付一帧的钱；
   回跳（拖播放头）时才重开迭代器，那一次贵是可以接受的。
2. **补队列排在当前帧上屏之后**（`setTimeout(0)`）。在 `draw()` 里就地补会把
   解码压进同一个 rAF 任务，这一帧的上屏跟着往后推 —— 缓存开着反而更卡。
3. **命中判定按帧号、带 1.5 帧容差**（`pickFromQueue`）。播放头按音频钟走，每
   tick 前进 1–2 帧，「必须精确等于本帧」会把跳过的那一帧变成一次未命中；队列
   时间戳也改成落在帧栅格上（`f / fps`），否则浮点相位会让队列整体偏一帧。
   **绝不取未来帧**（超过半帧的不取），否则剪切点会提前露出下一个镜头。
4. **落后就跳帧，没货就重复上一帧**（`fill` 的 `CATCHUP_FRAMES` + `draw` 的 hold）。
   落后时把中间帧**非线性解码掉**（重开迭代器），只补最近的三帧；确实一帧都没有
   可重复的就 hold 住 —— 见 §5 的正反馈。
5. **停在缓存段里就把解码器开着**（`prime` 暂停时也调）。按播放键之后头 150–200 ms
   要读 blob、建 `Input`、定位关键帧，那一段没缓存可放 —— 实测就是「刚播那一下卡」。

## 6. 磁盘

`<工程目录>/cache/preview/<sig>-<from>.mp4` + 同名 `.json`（帧区间 / 签名 / 尺寸 /
帧率 / 字节数 / 写入时刻）。

- 进 `PROJECT_DIRS`，进 `src/project/AGENTS.md` 的「可丢弃」清单；
  `saveProject` / `autosave` / 打开工程都不碰它。
- **不进** `package.ts` 的产物（它只打 `project.json` + 台账里的素材；已核对）。
- 打开工程时扫一遍：索引里没有的 `.mp4`（上次崩在中途）、版本不符的 `.json` 直接删。
- **回收分两路**：GC 按**几何**删（落在计划区间之外的整段永远不会再播）；
  内容过期的条目在**被播到**的时候删（判内容要给每个条目算签名，别塞进 GC）。
- 设置页有「清空预览缓存」，显示当前占用。

## 7. 设置

`UiPrefs.previewCache = { enabled, budgetMB }`，默认**开**、1 GB。

关掉就是完全关掉：不读不写不扫。它不是「少用一点」，是「这个功能不存在」。
按 §1.9 的例外条款，预览缓存属于「应用偏好 + 壳层磁盘动作」，不要求 Agent 可达。

## 8. 风险

| 风险 | 处置 |
|---|---|
| 编码器占用主线程 | 一帧只花 2–4 ms，且间隔 ≥ 1000/24 s（占空比 1/4）；播放中永不生成 |
| 烘焙抢可见画布 / 冻住预览 | 渲进离屏目标（`render/bake-surface.ts`），可见画布与预览那台合成器都不经过 |
| **改一处炸全部** | 每段各自签名（§3）：段外的编辑不影响本段 |
| **播放掉出缓存的正反馈**（一帧没追上 ⇒ 帧率更低 ⇒ 更追不上） | 没货就重复上一帧、落后就跳帧，播放中永不回精确合成（§5） |
| 大量编辑 ⇒ 磁盘被旧内容塞满 | 内容过期的条目在播到时删；几何上已不存在的整段由 GC 删；再按预算 LRU |
| 生成中途崩溃留下半个 MP4 | 索引是唯一真相，没有索引条目的文件在打开时删掉 |
| 编码器不存在（无 WebCodecs H.264） | 直接不启用，设置项置灰说明原因（不静默） |
| **预览缓冲是奇数宽高**（H.264 一律拒绝，报出来的却是「没有编码器」） | 缓冲尺寸取偶（`core/dims.ts`），烘焙目标按它建 |
| 用户以为「缓存了 = 精确」 | 播放用缓存；停手 250 ms 之后、以及每一帧定格都走精确渲染 |

## 10. 守卫

- **单测**：签名**对段外编辑不敏感**、对段内 / 全局（seed / fps / 尺寸 / 素材指纹）
  敏感（`tests/unit/preview-cache.test.ts`）—— 这条是「改 50 s 处不炸 0 s」的本体。
- **单测**：回收只删「几何上已不在计划区间内」的条目，且总量回到预算的 80%。
- **单测**：`evenDims` 幂等、退化输入给 ≥2、奇数向下取偶（`tests/unit/dims.test.ts`）。
- **e2e**：预览缓冲恒为偶数（含降质档位），且这个尺寸问 H.264 至少有一档可用。
- **e2e**：烘焙期间预览仍在逐帧渲染（数 `renderFrame` 调用；冻结时是 0）。
- **e2e**：同一 t 的缓存帧与 `renderFrame` 的整帧均值差 < 3，且上下两半的亮度
  关系一致（后者专抓「回读上下颠倒」）。
- **e2e**：缓存关闭时不产生任何缓存条。
- **e2e**：播放一段烘好的区间，命中率 ≥ 85%，且**精确渲染 ≤ 2 次**（只有开头那
  1–2 帧允许，因为播放器还没打开、没有可重复的帧）。
- **e2e**：改远处的片段 ⇒ 这一段仍有效；改段内 ⇒ 必须失效。
- **e2e**：拖动播放头 250 ms 内**一次精确渲染都不能有**，停手之后必须补一次。
- **e2e**：改一个参数 ⇒ 旧条目不再命中（断言解码次数 0、渲染次数 > 0）。**仍未做**。

**接线（2026-11-18 补完）**：

- `tick()` 三条分支：播放 → `draw()`；暂停且 250 ms 内动过播放头 → `scrubbing()`；
  其余（停顿定格）→ `renderFrame()`。`prime(playT)` **每帧都调**（暂停也调，见
  §5.1 第 5 条）；`markPlayed()` 放行生成闸；帧末 `pump()` 推进后台烘焙。
- 生成闸两道：**播放过一次**才允许烘（否则「打开工程静置 1.5 s」就开始烘一段，
  而用户可能只是想看看时间轴）；播放中不烘，播完由 `pause()` 重新排一次。
- `setEnabled` 接在 `UiPrefs.previewCache` 的四条同步线上；`projectDir` 的 setter
  调 `reset()`（换工程 ⇒ 句柄换了，索引与解码器都作废）。
- 设置页：「预览渲染缓存」勾选框 + 「清空预览缓存」，`testid` 是
  `setting-preview-cache(-clear)`。

**三个必须知道的行为**：

1. **烘焙不占用预览**：帧渲进 `bake-surface` 的离屏目标再回读，`tick` 里**没有**
   「编码中就 return」那条分支了。谁把它改回 `runExport` + 可见画布，代价立刻
   回到「烘几秒、画面冻几秒」（见 `docs/preview-cache.md` 与
   `src/render/AGENTS.md`）。
2. **默认开**，所以第一次打开带工程的目录会多出 `cache/preview/`（`ensure` 在
   `setEnabled` 里跑）。不想要就在设置里关掉，关掉之后不读不写不扫。
3. `assetsRev` 目前传空串：`Asset.hash` 是可选字段（`core/schema.ts`），台账里
   没填就无从比较。**linked 素材原地换字节不会击穿缓存**，与排版位图缓存同一个已知限制。

**仍未做**：E2E 守卫「改参数后不再命中」、`capacity.ts::previewCacheMB`
（预算现在直接读 `UiPrefs.previewCacheMB`）。

## 12. 时间轴上的进度（标尺底边那条细线）

三种状态**互斥、铺满每个计划区间**（`grid-draw.ts::drawCacheBand`，数据来自
`appState.cacheStrip()`，切片在 `core/preview-cache.ts::cachePieces`）：

| 状态 | 形态 | 含义 |
|---|---|---|
| `missing` | **红**实线 | 没有缓存 —— 这一段会卡 |
| `encoding` | **绿虚线** | 正在烘（虚线随进度变长），还不能用缓存预览 |
| `ready` | 绿**实线** | 已烘好、可预览 |

四条纪律：

1. **不用 alpha 表达浓淡**：亮色主题下 50% 绿和 70% 绿几乎分不出来（用户实测
   反馈）。三态用两个实色 + 线型区分。
2. **线宽是「能看见」的最小值**（1–1.5px）。它横跨整条时间轴，再粗就抢片段本身。
3. **必须画在 `drawRuler` 里面**：标尺每次只重画可见的那一小段（滚动时只补缺口），
   在外面补画清不掉旧像素 —— 表现就是「缓存烘完了、缩放一下还能看见残留的绿虚线」。
4. **虚线要实时长**：烘焙进度（`encodingRange().done`）按「已码到的帧」切出
   `encoding` 段。重画由 `onStatus` 驱动（`noteCacheProgress`，150 ms 节流），
   **「空闲」那条通知必须排在落盘之后** —— 否则条子上永远少最后一片（踩过）。
